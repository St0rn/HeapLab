Entrée d'analyse

Traitement local
Simulation statique bornée : suit main(), des fonctions, if/switch/boucles, certains structs et new/delete. Les appels inconnus, bibliothèques, macros conditionnelles et pointeurs complexes restent approximatifs. Le vrai programme n’est exécuté qu’en mode natif sur autorisation.

Options de programme → hypothèse de heap

Une aide --help ne révèle pas les allocations internes. Décris les relations supposées entre les options et les opérations mémoire : le schéma obtenu sera explicitement hypothétique.

Seules les règles que tu écris sont simulées : l’outil ne devine pas malloc à partir de --help.
Syntaxes : A = malloc(24), B = calloc(4, 8), A = realloc(A, 48), free(A), strcpy(A, argv[1]), write(A, "ABC"), fill(A, 0x41, 40), memcpy(A, argv[1], 30).
Les chunks suivent un modèle pédagogique inspiré de glibc 64 bits. Les adresses, les réutilisations et les bins sont simulés, pas observés dans un processus.

Importe une trace JSON d'allocations existante. Chaque événement : {"op":"malloc","var":"A","size":24}, {"op":"free","var":"A"}, {"op":"fill","var":"A","byte":65,"count":40}.

Trace d'événements logique (noms de pointeurs), pas dump brut de GDB.

Vérification du moteur local…
Danger : un ELF peut exécuter du code arbitraire. Limites de ressources ≠ bac à sable. Utiliser une VM isolée sans secrets et sans réseau pour les fichiers non fiables. Sans serveur Linux, utilise les autres onglets, toujours fonctionnels.

La trace native intercepte malloc/calloc/realloc/free, collecte des snapshots bornés aux appels interceptés et lit les champs de taille glibc. Elle ne surveille pas chaque instruction ni les bins internes.
